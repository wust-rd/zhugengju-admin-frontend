## 1. 业务故事（端到端）

三类角色，全部挂在「前期规划-片区策划申报审查」菜单下（角色已在后台建档）：

| 角色名称 | 角色代码 | 说明 |
|----------|----------|------|
| 填报单位 | `esp_pqchsbsc_fill_unit` | 区级填报单位，新增/编辑片区策划方案 |
| 联合审查单位 | `esp_pqchsbsc_joint_review` | 市级部门（市资建局/市发改委/市经信局/市商务局/市教育局/市卫健委/市财政局/市交通局/市水务局/市消防局），按主审单位指派参与联审 |
| 主审单位 | `esp_pqchsbsc_main_review` | 市住更局，牵头审查并出最终结论 |

同一个账号可同时拥有多个角色，判定优先级：**主审 > 联合审查 > 填报**（前端 `roleOfCurrentUser()`）。

### 故事 1 · 填报单位申报

1. 填报单位在「方案填报」页 **Tab② 待审查片区填报** 点「新增」，填写 8 个区块（基本信息 / 体检情况 /
   功能策划 / 城市设计 / 规划调整 / 项目情况 / 资金方案 / 附件材料）；
2. 点 **暂存** → 片区状态 = **未提交**（草稿，**不做必填校验**，可继续编辑/删除）；
3. 点 **提交** → **逐区块必填校验**（校验不过会定位到第一个问题区块，见第 5 章）→ 落库 →
   状态 = **审核中**；此后填报单位**只能查看**（列表操作列仅「查看」）；
4. 被主审单位退回后（状态 = **退回修改**），填报单位可「查看 / 编辑 / 修改意见」，
   在**编辑表单里改完再提交**（列表不再提供提交入口），状态回到 **审核中**。

### 故事 2 · 主审单位审查

1. 主审单位在「策划方案审查」列表看到所有**已提交**片区（未提交的草稿不进审查），
   状态为 **审核中** 时可点「审查」；
2. 审查页 = 只读填报内容 + 审查记录 + 底部「片区申报审核」填写区；顶部三个按钮：
   **导出 / 联合审查 / 提交**；
3. 「提交」按审核结果分支：
   - **通过** → 状态 = **通过**，流程结束（终态）；
   - **退回修改** → 状态 = **退回修改**，回到填报单位修改；
4. 「联合审查」→ 弹窗多选联合审查单位 → **点确定即推送**（弹窗里主审已填内容不作数）：
   状态 = **联合审查中**，轮次 +1，被选单位收到**系统通知**；
5. 主审单位**不必等**联审单位全部提交，可随时再出结论（通过 / 退回修改 / 再次联合审查）；
6. 再次联合审查 = 第二轮（第三次、第四次…），直到主审点「通过」结束。

### 故事 3 · 联合审查单位

1. 收到系统通知后，在自己账号的「策划方案审查」列表里，被指派且未提交的片区显示
   **待我审查** 标记，可点「审查」；
2. 审查页底部「片区申报审核」：审核结果 **通过 / 退回修改 / 不涉及**（三选一，必填）+
   审核意见 + 附件；**每轮每个单位只能提交一次，提交后不可修改**；
3. 可见范围：**只看自己被指派那一轮**的记录 + **与该轮关联的那一条主审意见**
   （本轮推送之后、下一轮推送之前的主审意见）——自己没提交也能看到主审后来的结论；
   不展示其他单位的意见与进度。

### 故事 4 · 审查信息可见范围（业务原则）

| 查看者 | 可见范围 |
|--------|----------|
| 主审单位 | 该片区**全部**审查信息（各轮联审单位意见 + 主审历次意见） |
| 填报单位 | **只看主审单位的审查记录**（列表「查看」与「修改意见」弹窗同口径） |
| 联合审查单位 | 只看自己那一轮（见故事 3） |
| 无审查角色 | 只读、可见全部记录，不能提交 |

| 页面 | 路由 / 组件位置 | 文件 |

### 2.1 状态机（五态）

| 状态 | 枚举值 | 颜色 | 进入方式 |
|------|--------|------|----------|
| 未提交 | `unsubmitted` | 红 | 填报单位「暂存」 |
| 审核中 | `reviewing` | 蓝 | 填报单位「提交」（含退回后重新提交） |
| 退回修改 | `returned` | 橙 | 主审「退回修改」 |
| 联合审查中 | `jointReviewing` | 紫 | 主审发起联合审查（推送） |
| 通过 | `passed` | 绿 | 主审「通过」（终态） |

> 填报单位侧展示：`jointReviewing` 一律显示为「审核中」（`fillSideStatusOf`）。
> **联合审查单位侧是另一套逻辑，只有两态**：`审核中`（被指派但自己还没提交）/ `已审核`
> （自己提交过就算已审核）—— 与主审看到的五态互不影响（`jointSideStatusOf`）。

### 2.1.1 列表数据范围（按角色）

| 角色 | 审查列表能看到什么 |
|------|--------------------|
| 主审单位 | **所有填报单位**已提交的片区（未提交草稿不进审查），状态列＝五态 |
| 联合审查单位 | **只有被发起联合审查、且本轮/往轮指派给本单位的片区**（没被指派过的一律不显示），状态列＝两态（审核中 / 已审核） |
| 填报单位 / 无审查角色 | 只读（前端现状），后续按权限码与数据范围收敛 |

### 2.2 状态 × 角色 → 可执行动作

| 状态 | 填报单位 | 主审单位 | 联合审查单位（被指派且未提交） |
|------|----------|----------|--------------------------------|
| 未提交 | 查看 / 编辑 / 删除 | 不可见 | 不可见 |
| 审核中 | 仅查看 | 查看 / 审查 | 不可见 |
| 退回修改 | 查看 / 编辑 / 修改意见 | 查看 / 审查 | 不可见 |
| 联合审查中 | 仅查看（显示「审核中」） | 查看 / 审查（含再次联合审查） | 查看 / 审查（一次） |
| 通过 | 仅查看 | 仅查看 | 仅查看 |

### 2.3 审查页构成

1. **填报内容只读**：8 个区块（基本信息 / 体检情况 / 功能策划 / 城市设计 / 规划调整 / 项目情况 /
   资金方案 / 附件材料）；
2. **审查记录时间线**（按时间**正序**）：轮次块（`第N次联合审查单位：` + **每个联审单位一个 tab，
   tab 上标「已审查/未审查」**，点击切换该单位意见）+ 主审意见卡，两类混合按时间排列；
3. **片区申报审核**填写区：审核结果 + 审核意见（≤1000 字）+ 附件（MinIO 上传，多选）；
4. 顶部按钮：**导出**（PDF 打印版式 / Word 真文档，含审查记录）、**联合审查**（仅主审）、
   **提交**（二次确认后提交）。

| # | 标签 | 字段（保存键） | 后端文件位 field_code | 格式 | 必填 |

## 3. 数据模型与后端改动清单

### 3.1 现有（已对接，不改语义）

- `ESP_MAP_AREA`：片区主表（`is_approve` 1=已批准存量 / 2=待审查填报；`batch` 存批次或申报年份；
  `approval_files` 等文件位；`scope_line` WKT 等）；
- `ESP_MAP_PROJECT`：片区项目行（`fill_flag` 0=存量 / 1=填报，`p_uid` 唯一号）；
- `ESP_FILE_URL`：文件位（`a_uid` + `field_code` + 文件名/URL/size，本项目直链 MinIO）；
- `js_msg_inner`：框架站内消息（本模块用于联合审查推送通知）。

### 3.2 需要新增

**① 审核状态列**（★ 最基本，前端假数据全指望它下线）

```sql
ALTER TABLE ESP_MAP_AREA ADD review_status varchar(20);  -- unsubmitted/reviewing/returned/jointReviewing/passed
```

- 列表 / 详情回显 `reviewStatus`；保存时按动作写入（暂存 → `unsubmitted`，提交 → `reviewing`）；
- 存量数据迁移建议：已批准片区（`is_approve=1`）置 `passed`，待审查片区按业务确认。

**② 审查记录表**（主审 + 各轮联审意见）

```sql
CREATE TABLE ESP_REVIEW_RECORD (
  id            varchar(64) PRIMARY KEY,
  a_uid         varchar(64),   -- 片区（ESP_MAP_AREA.a_uid）
  role          varchar(10),   -- main=主审 / joint=联合审查
  unit_code     varchar(64),   -- 审查单位编码（主审为市住更局；联审为部门编码）
  unit_name     varchar(200),  -- 审查单位名称（快照）
  round_no      int,           -- 联合审查轮次（主审记录为空）
  conclusion    varchar(20),   -- passed=通过 / returned=退回修改 / na=不涉及（仅联审可选）
  opinion       varchar(3000), -- 审核意见
  review_time   datetime,      -- 审查时间
  create_by / create_date …
);
-- 附件：并入 ESP_FILE_URL（field_code = review_record，biz_id = 记录 id）或本表存 JSON
```

**③ 联合审查轮次分配表**

```sql
CREATE TABLE ESP_JOINT_ROUND (
  id           varchar(64) PRIMARY KEY,
  a_uid        varchar(64),
  round_no     int,            -- 1,2,3…
  unit_codes   varchar(1000),  -- 逗号分隔的联审单位编码
  unit_names   varchar(1000),  -- 名称快照（消息与展示用）
  push_time    datetime,
  push_user    varchar(64),    -- 发起的主审用户
  create_by / create_date …
);
```

**④ 联审单位字典**（前端现硬编码 10 家，需接口下发「单位编码 + 名称」，建议 `js_sys_office` 或
`esp` 自有字典表）。

## 4. 接口清单

### 4.1 已对接（保留；仅需扩展 reviewStatus 与提交类型）

| 接口 | 方法 | 前端函数 | 说明 |
|------|------|----------|------|
| `/a/esp/schemeFill/page` | GET | `schemeFillPage` | 片区分页：`pageNum/pageSize/isApprove(1/2)/name/district/funcType/batch`；返回 `{total,list}`，行含 `id/code/aUid/isApprove/name/district/areaHa/funcTypes/batch/invest/reportTime/reportOrg`（**新增 `reviewStatus`**） |
| `/a/esp/schemeFill/form` | GET | `schemeFillForm` | 填报详情全字段（新增 `reviewStatus`） |
| `/a/esp/schemeFill/save` | POST | `schemeFillSave` | 全量保存。**新增入参 `submitType: 'draft' \| 'submit'`**：draft=暂存（宽校验，状态→未提交）、submit=提交（服务端必填校验，状态→审核中） |
| `/a/esp/schemeFill/delete` | POST | `schemeFillDelete` | 删除（仅待审查片区、仅未提交/退回修改可删） |
| `/a/esp/file/upload` | POST | `espFileUpload` | 单文件上传 MinIO，返回 `[{fileName,url,objectKey,size}]` |
| `/a/esp/schemeFill/parseVector` | POST | `schemeFillParseVector` | 矢量解析（dwg/dxf → WKT） |
| `/a/msg/msgInner/save` | POST | （框架已有） | 站内消息发送，本模块用于联合审查通知 |

响应协议：`{code, msg, data}`，`code=200` 成功、`400` 业务错误（`msg` 直接 toast 展示）、`500` 系统异常。

### 4.2 需要新增（建议权限码见第 6 章）

#### ① 审查列表 `GET /a/esp/schemeReview/page`

- 入参：`pageNum,pageSize,name,district,batch,reviewStatus,scope`；**数据范围由后端按登录角色决定**：
  - 主审单位 → 全部填报单位「已提交」的片区（`review_status != 'unsubmitted'`）；
  - 联合审查单位 → **只返回被发起联合审查且指派到本单位的片区**（`ESP_JOINT_ROUND.unit_codes`
    含本单位部门的片区；没被指派过的不返回）；
  - 填报单位 → 本单位片区（该角色主要用「方案填报」页）。
- 返回：与 `schemeFill/page` 同行结构 + 两个状态字段：
  ```json
  {
    "reviewStatus": "jointReviewing",   // 主审/填报口径：五态
    "jointStatus": "reviewing",         // 联审单位口径：reviewing 审核中 / reviewed 已审核 / null 非联审相关
    "myTaskStatus": "pending"           // 当前账号待办：pending 待我审查 / submitted 已提交 / none
  }
  ```
- 前端调用点：`scheme-review/list.vue` 的 `fetchReviewRows()`（当前用 `schemeFill/page?isApprove=2`
  + 前端「未提交过滤 + 角色可见性过滤」，替换后即可去掉过滤与种子假数据）。

#### ② 审查页详情 `GET /a/esp/schemeReview/form?id={id}`

- 返回：
  ```json
  {
    "scheme": { "…同 schemeFill/form 全字段…", "reviewStatus": "jointReviewing" },
    "records": [
      { "id": "…", "role": "main", "unitCode": "…", "unitName": "武汉市住更局", "round": null,
        "conclusion": "returned", "opinion": "…", "files": [{ "name": "…", "url": "…", "objectKey": "…", "size": 1024 }],
        "reviewTime": "2026-09-18 09:30:00" }
    ],
    "rounds": [
      { "round": 1, "units": [{ "code": "…", "name": "市水务局" }], "pushTime": "2026-09-18 10:20:00" }
    ],
    "actions": { "canMainReview": true, "canJointReview": false, "canJointPush": true, "canEdit": false }
  }
  ```
- `actions` 由后端按「登录人角色 + 状态 + 轮次指派 + 是否已提交」计算，前端按它渲染按钮
  （避免前端各自判断，后续接权限更稳）。

#### ③ 主审提交结论 `POST /a/esp/schemeReview/mainSubmit`

- 入参：`{ id, conclusion: 'passed'|'returned', opinion, files: [{name,url,objectKey,size}] }`；
- 行为：写 `ESP_REVIEW_RECORD`（role=main）+ 更新 `review_status`
  （passed → `passed` 终态；returned → `returned`）；
- 返回：`{ reviewStatus, recordId }`。

#### ④ 发起联合审查 `POST /a/esp/schemeReview/jointPush`

- 入参：`{ id, unitCodes: ['…','…'] }`（多选，至少 1 个）；
- 行为：`ESP_JOINT_ROUND` 插入一轮（round_no = 已有最大轮次 + 1）→ `review_status = jointReviewing`
  → **给所选单位发站内消息**（推荐后端在本接口内部发送，前端已临时直调 `msg/msgInner/save`，
  见 4.3）；
- 返回：`{ round, pushTime }`。

#### ⑤ 联审单位提交意见 `POST /a/esp/schemeReview/jointSubmit`

- 入参：`{ id, conclusion: 'passed'|'returned'|'na', opinion, files }`；
- 行为：校验「当前轮次是否指派给登录人」「本轮是否已提交」（**已提交直接拒绝，不允许覆盖**）→
  写 `ESP_REVIEW_RECORD`（role=joint，round_no=当前轮）；**不改 review_status**（仍 `jointReviewing`）；
- 返回：`{ recordId }`。

#### ⑥ 我的待办 `GET /a/esp/schemeReview/todo`

- 返回：`{ jointPending: 3, items: [{ id, name, round, pushTime }] }`（联审单位登录后提示
  「您有 N 个片区待联合审查」，并可用于首页/通知角标）。

#### ⑦ 字典 `GET /a/esp/schemeReview/dict`

- 返回：
  ```json
  {
    "jointUnits": [{ "code": "…", "name": "市水务局" }],
    "districts": ["汉阳区", "…"],
    "funcTypes": ["TOD", "EOD", "IOD", "SOD", "COD", "HOD", "POD"],
    "batches": ["第一批", "第二批"]
  }
  ```
- 前端现状：联审单位硬编码 10 家（`JOINT_REVIEW_UNITS`）、行政区/功能定位/批次硬编码；
  接口就绪后全部替换。

### 4.3 通知（联合审查推送）

- 现状：前端在推送成功后**直调框架站内消息** `POST /a/msg/msgInner/save`：
  `receiveType='3'`（角色）、`receiveCodes='esp_pqchsbsc_joint_review'`、`msgTitle`
  `【片区策划方案审查】{片区名} 发起第N次联合审查`、`msgContent` 列出本次被选单位。
  → 所有拥有「联合审查单位」角色的账号都会在**系统通知 / 站内消息**里看到；
- **建议**：改由后端在 `jointPush` 内发送，并**按部门（receiveType='2' + 部门编码）精确推送**
  给所选单位；同时返回该片区在各单位下的「未读/待办」状态（前端 ⑥ 接口展示）；
- 前端发送失败不阻断流转（仅提示），所以后端实现后前端删掉 4.3 的临时调用即可。

## 5. 校验与业务规则

### 5.1 前端校验（已启用）

- **暂存**：不校验（草稿允许留空）；
- **提交**：逐区块必填校验，失败滚动定位到第一个问题区块并 toast「存在未完善的必填项，已定位到对应区块」。

提交时的必填项（红星字段）：

| 区块 | 必填字段 |
|------|----------|
| 片区基本信息 | 片区名称、**申报年份**、行政区、片区规模（公顷）、片区概况、片区概况图片、片区范围 |
| 片区体检情况 | 问题整治清单、发展机遇清单、更新诉求清单（三个清单各至少 1 条） |
| 片区功能策划 | 总体目标、片区功能定位（多选）、功能策划、策划图册 |
| 片区项目情况 | 每个项目行：项目名称、改造类别、主要建设内容 |
| 片区资金方案 | 总体投资估算 |
| 城市设计 / 规划调整 / 附件材料 | 暂不校验（见 6.4 待确认） |

### 5.2 后端轻校验（建议保留并补齐）

- 同名片区唯一；字段字数上限（总体目标 ≤200、城市设计内容 ≤300、审核意见 ≤1000…）；
- 项目起止时间序（竣工 ≥ 开工）、片区起止时间序（endTime ≥ startTime）；
- 提交时复核必填（前端校验可绕过）；状态流转合法性（见 2.2 矩阵），非法流转返回 400 + msg。

## 6. 权限与数据范围

### 6.1 角色代码（已在后台建档）

`esp_pqchsbsc_fill_unit`（填报单位，排序 60）、`esp_pqchsbsc_joint_review`（联合审查单位，80）、
`esp_pqchsbsc_main_review`（主审单位，70）；菜单归属：前期规划-片区策划申报审查。

### 6.2 权限码建议

| 权限码 | 说明 |
|--------|------|
| `esp:schemeFill:view` | 查看填报列表/详情（三个角色都需要） |
| `esp:schemeFill:edit` | 新增/编辑/暂存/提交/删除自己的片区（填报单位） |
| `esp:schemeReview:view` | 进入审查列表与审查页 |
| `esp:schemeReview:main` | 主审提交结论、发起联合审查 |
| `esp:schemeReview:joint` | 联合审查单位提交意见 |

### 6.3 数据范围

- 填报单位：仅本单位（`create_by` 部门）填报的片区；
- **主审单位：全部填报单位已提交的片区**（不按填报单位过滤）；
- **联合审查单位：只返回「被发起联合审查且指派到本单位」的片区**（`ESP_JOINT_ROUND.unit_codes`
  含本单位部门编码）；列表状态用**单独的两态**（审核中 / 已审核），与主审的五态无关；
- 无审查角色：只读（前端已按此渲染，后端接口需同样过滤）。

### 6.4 待确认（请产品/后端拍板）

1. 联审单位字典的数据来源（`js_sys_office` 部门 or 自建字典），以及**按部门精确推送通知**的实现方式；
2. 附件材料的 8 个红星位，**提交时是否必须已上传**（前端目前不拦截，仅红星提示）；
3. 城市设计与规划调整区块是否需要必填校验；
4. 退回修改后是否需要**重新走联合审查**（现规则：填报单位重提 → 直接回到主审，不重走联审）；
5. 存量已批准片区（`is_approve=1`）的 `review_status` 初始值；
6. 联审单位「不涉及」是否计入「已提交」（现计入，且不阻塞主审）；
7. 审查记录与联合轮次是否需要**删除/撤销**能力（现无，提交后不可修改）。
